#+title: Issue #1 — RFPP intent parser root-cause repair
#+date: 2026-10-10

* Scope and cause
Target: =wiki20260401=, PostgreSQL 18 on port 5434, =service=wiki=.
This supersedes the remediation status in =issue-1-audit-log.org=; that log
and the original report retain their historical evidence unchanged.

SQL04 extracted the first matching tier token, mapped bare “extended” to
ECP, and defaulted direction using request wording plus administrator response
codes. This confounded duration with tier, origins with destinations, and
intent with outcome. Fixing selected rows alone would reproduce the defect
on the next build.

* Implementation
The analysis repository now has one shared, versioned request-only parser:
=../20261001/wpp-analysis/sql/04a_rfpp_intent_parser.sql=.
Its only input is =reason=; granted and denied requests take the same path.
ECP requires extended-confirmed wording, ECP, or label-context EC. Bare
“extended” is never sufficient. Explicit from/to constructions select the
destination and preserve the stated origin. Only none/semi/ECP/full have an
ordered transition hierarchy; other transitions retain explicit direction
or use =change=. Duration extension is a separate flag; =increase= retains
the legacy coarse meaning for a simple positive request, including renewal.

Alternatives retain a target set and no single tier. Ambiguous and amended
requests retain uncertainty. Missing evidence no longer defaults to increase.
Body inference requires request wording, rather than the first historical tier
mention. A generic heading can precede the actual bold label. Metadata records
version, rule, evidence, raw/normalised label, origin, target set, action basis,
and uncertainty. The original =reason= remains unchanged.

SQL04 calls =04b_rfpp_request_intent.sql=, which uses that parser. Shared
=04c_rfpp_request_match.sql= handles protection-event associations; the scoped
migration calls it only for changed-action IDs. Unknown direction can retain
an independent candidate log association but cannot certify =treated_by_log=.
Applied levels come from event records, never from requested levels.

These scripts deliberately refuse unsafe repeated application. The staging
script creates the original snapshot once; restaging updates candidates only
while the run is staged. The migration defaults to a full rehearsal ending
in ROLLBACK (the nullable metadata column is added independently). A parser
signature and hashes of every original row reject changed code/source state.
The full destructive SQL04 was NOT rerun against the live database.

The initial migration rehearsal completed with preservation checks and
ROLLBACK; subsequent sample review refined nested labels and alternatives.
Its counts in =logs/issue-1-rehearsal-20261010.log= are historical candidate
counts. The final applied report is authoritative for final counts.

* Validation and evidence
Regression tests cover duration phrases, both directions, alternative tiers,
negation, amended text, long labels/body text, normalisation, missing evidence,
body history versus requests, nested headings, and the ten historical fixtures.
The test runner is read-only and checks semantic outputs, not implementation
text. Seven unittest methods include multiple subcases.

The full population is evaluated, with confusion tables for actions and tiers,
changed IDs, status counts, and strata by year/outcome/old/new evidence source.
A deterministic sample selects up to three rows per status/source/tier/change
stratum. This is diagnostic review, not a blinded human validation study or
an estimated error rate. Sample review prompted added regression cases.

The migration transaction asserts preservation of every raw, identity,
outcome, and unrelated derived field by comparing complete rows minus an
explicit whitelist. It verifies stage/output agreement and unchanged matching
fields outside the changed-action scope. All protection events are read-only.
Stable RFPP identity uniqueness is enforced by primary keys. No raw request,
response, administrative outcome, or event-level record is corrected by copying
an inferred intent value into it.

* Reversibility
=analysis.rfpp_request_pre_intent_v2= retains every original row and field.
=analysis.rfpp_intent_v2_stage= retains old classifications, complete proposed
intent, and original row hashes. =analysis.rfpp_intent_v2_changes= records all
changed legacy records, old/new classifications and links, and after hashes.
Metadata is attached to the full population, including unchanged records.
=analysis.rfpp_intent_v2_run= records parser signature and application state.

=rollback_rfpp_intent_v2.sql= is a prepared rollback, defaulting to ROLLBACK.
It verifies the entire post-repair population and refuses to overwrite later
changes, restores only the repair's derived fields from the preserved snapshot,
and asserts exact equality with original rows (apart from the nullable new
metadata column). It was executed to reverse the encoding-defective first attempt; the final repair remains applied. The preserved
Parquet must be restored separately if rolling back the database. Parser source
must also be reverted for future rebuilds; do not delete the audit tables.

* Downstream dependencies and limits
The direct mainspace granted/denied request cache is refreshed from the repaired
source, retaining =rfpp_request.pre-intent-v2.parquet= and both hashes. Other
frozen sample tables and model outputs retain their original versions.
=analysis.rfpp_intent_v2_invalidations= lists RFPP-ID-bearing analytical tables
and their direct intersections with changed IDs. This count is not a complete
impact bound: changed selection or grouped duration medians can affect other
requests and inherited controls too.

Controlled rebuild order: SQL20 request eligibility and tier/year pseudo-expiry
medians, sampled page/control frames, their panels/outcome caches, then IV strata
and estimates/reports (including scripts 30, 40 and 80 where dependent).
Preserve old samples/results for comparison. The old y3/topic/sample caches
must not be assumed to share the corrected source population merely because
the direct request cache is current. This repair does not certify previously
published estimates; the GitHub issue remains open for downstream rebuilding
and independent validation.

The parser is deliberately conservative, not a complete language interpreter.
Unsupported formulations, quoted/contextual language, unrelated strike-through,
and restriction-type versus tier combinations still require review. In
particular, move/create/upload requests mix dimensions in the legacy tier
vocabulary. Chronology cannot be established from final archived text alone.
No population accuracy percentage is claimed. The separate ECR/pre-existing
state and log-linkage validity questions remain outside this root-cause fix.

* Encoding correction during end-to-end validation
The first committed candidate passed classification and raw-field checks, but
Parquet validation detected invalid UTF-8 in derived normalised labels.
The new normalizer used =translate= with multibyte punctuation; in this
SQL_ASCII database that operates on bytes and could remove bytes from unrelated
Unicode characters. Raw requests and the original Parquet were unaffected.

The guarded rollback was actually executed and its exact original-row equality
assertion passed. First-application audit tables were archived as
=rfpp_intent_v2_first_apply_changes=, =rfpp_intent_v2_first_apply_invalidations=,
and =rfpp_intent_v2_first_run=. Disk artifacts containing
=-superseded-encoding= describe that reversed attempt, not the final state.
The temporary failed export was removed; the active cache was never replaced
by the invalid export.

Normalization now replaces complete Unicode dash sequences before applying
ASCII-only =translate=. A seventh regression method checks bullets, Unicode
text, and en/em dashes against the live SQL_ASCII database. Every staged JSON
record is additionally checked with strict UTF-8 decoding before application.
=restage_rfpp_after_encoding_fix.sql= records the one-time recovery sequence.
Final counts and hashes below supersede preliminary figures.
